# FITS — Questions difficiles pour l'oral E7B

Réponses courtes à reformuler avec tes mots et à relier au `DOSSIER_REX_E7B.md`. Une preuve de fonctionnement, une mesure hors ligne et un retour client sont trois niveaux distincts. **Aucun retour explicite de client ou d'utilisateur, distinct des votes du compte test, n'a été recueilli.**

| Question possible du jury | Réponse défendable et preuve à montrer |
|---|---|
| **1. Où est le « Big Data » avec seulement 69 avis ?** | FITS est un prototype à faible volume ; je ne revendique pas un traitement massif. J'ai mesuré volume, vélocité et variété et défini des seuils de croissance avant d'ajouter une infrastructure distribuée. `ANALYSE_BIG_DATA.md`. |
| **2. Pourquoi PostgreSQL et MongoDB ?** | PostgreSQL porte les relations métier et les avis ; Mongo stocke les logs et une voie photo, hors ML. À cette échelle, le gain de Mongo n'est pas démontré et son coût de maintenance/suppression est réel. `ANALYSE_POSTGRESQL.md`, `ANALYSE_MONGODB.md`. |
| **3. Pourquoi pas Spark, Kafka ou Hadoop ?** | Aucune taille ni vitesse observée ne justifie ces outils. Le vrai problème mesuré est la qualité/diversité des avis, non la capacité de calcul distribuée. |
| **4. Comment les 69 avis deviennent-ils 64 lignes ML ?** | Cinq avis ont une température nulle et sont exclus. Les 64 lignes restantes comptent 42 likes et 22 dislikes ; le constructeur vérifie aussi types, propriété de la tenue et composition. `QUALITE_DONNEES.md`, `trainingDataset.js`. |
| **5. Que signifie « seulement trois snapshots » ?** | Trois des 69 avis bruts ont un instantané valide des caractéristiques au vote. Pour les 66 autres, les vêtements actuels peuvent servir à reconstruire les features : si ces vêtements ont changé, il existe un risque de fuite temporelle. Je ne peux pas reconstituer leur état passé sans autre source. |
| **6. Avez-vous empêché toute fuite entre entraînement et test ?** | Le protocole empêche qu'une même tenue ou un vecteur de 85 features identique apparaisse des deux côtés ; label et ID de tenue sont exclus des features. Il ne supprime pas le risque temporel des anciens avis ni toutes les corrélations entre tenues partageant des vêtements. `evaluate_robust.py`, `ANALYSE_FINALE_ML.md`. |
| **7. Pourquoi une baseline qui dit toujours « like » obtient-elle 63,8 % ?** | Les likes sont majoritaires : 42/64, soit 65,6 % sur l'ensemble. À chaque séparation, la baseline apprend la classe majoritaire uniquement dans l'entraînement ; les proportions des ensembles de test varient. La moyenne des 30 accuracies de test est 63,8 %. `PERFORMANCES_ML.md`. |
| **8. Que veut dire RF 58,2 % contre 63,8 % ?** | Sur les mêmes 30 découpages groupés, le RF classe correctement moins d'avis en moyenne : **5,6 points d'accuracy de moins**. Il ne bat jamais la majorité sur ces 30 comparatifs appariés. Cela n'est pas une preuve universelle qu'il sera toujours moins bon, mais aucun gain n'est démontré ici. |
| **9. L'accuracy suffit-elle avec 42 likes et 22 dislikes ?** | Non. J'ai aussi rapporté balanced accuracy, précision, rappel, F1, ROC AUC et average precision. La baseline a un rappel like de 1 parce qu'elle prédit toujours like ; cela ne signifie pas qu'elle reconnaît les dislikes. Le RF reste aussi sous la baseline en balanced accuracy et AUC sur l'évaluation répétée. |
| **10. Pourquoi 85 features si 64 sont constantes ?** | Le schéma `outfit-v2` couvre températures, zones, couleurs et catégories possibles ; sur cet échantillon, seules 21 colonnes varient, avec redondances. Je ne prétends pas que 85 sont utiles. L'ablation hors ligne suggère que les indicateurs supplémentaires n'aident pas ici, sans prouver qu'ils seront inutiles sur d'autres utilisateurs. |
| **11. Si le RF est inférieur à la baseline, pourquoi FITS l'utilise-t-il encore ?** | C'est la limite actuelle : un modèle compatible est utilisé pour classer les candidats, sans garde-fou automatique contre la baseline. Je le présente comme une personnalisation **expérimentale**, pas comme une amélioration validée. Changer de modèle sur les mêmes 64 avis risquerait de sélectionner un résultat favorable par hasard ; il faut d'abord des données plus diverses et un protocole décidé à l'avance. |
| **12. Le fallback corrige-t-il un modèle faible ?** | Non. Le fallback au ratio de favoris sert quand aucun modèle compatible n'est disponible ; il ne s'active pas parce qu'un RF disponible est mauvais. `/predict` renvoie `model_used` et `reason`, ce qui rend la distinction visible. `ml-service/app.py`. |
| **13. Vos probabilités permettent-elles de classer les cinq tenues ?** | L'application les utilise pour choisir le meilleur des candidats, mais sa qualité de classement **n'est pas démontrée**. Elle n'enregistre pas les cinq candidats avec leurs scores ni un jugement sur chacun ; il serait abusif d'annoncer un NDCG@5. L'AUC sur avis retenus mesure autre chose. |
| **14. Pourquoi seulement 29 groupes pour 64 avis ?** | Beaucoup de tenues ont un vecteur de features identique. Onze vecteurs reçoivent des labels contradictoires ; les caractéristiques actuelles ne suffisent pas à séparer tous les avis. Les splits groupés évitent de tester sur une copie exacte d'un profil vu à l'entraînement. `ANALYSE_FINALE_ML.md`. |
| **15. Les modèles des utilisateurs sont-ils isolés ?** | Le backend dérive l'ID du JWT et l'envoie au service Python avec un secret de service. Python valide l'ID et lit/écrit `user_<id>.joblib` ; des tests vérifient modèles distincts et fallback de l'autre utilisateur. Cela ne constitue pas à lui seul un audit de sécurité de déploiement Internet. `mlClient.js`, `ml-service/app.py`, `ml-service/tests/test_app.py`. |
| **16. Un réentraînement peut-il corrompre un modèle existant ?** | Le service construit un candidat en mémoire puis écrit un fichier temporaire avant remplacement atomique ; le modèle valide reste en place si l'entraînement échoue. Un verrou sérialise les entraînements **dans un même processus**. Une coordination multi-processus n'est pas démontrée. |
| **17. Pourquoi ne pas indexer toutes les clés de recherche ?** | Sur 69 ou 271 lignes, `EXPLAIN ANALYZE` montre que les lectures sont rapides et que le scan séquentiel peut être optimal. Un index ajouterait du stockage et du coût en écriture sans gain mesuré ; je le testerais sur copie isolée si la charge augmente. `ANALYSE_POSTGRESQL.md`. |
| **18. FITS est-il conforme au RGPD ?** | Je ne le prétends pas. Les nouveaux logs d'authentification n'ajoutent plus e-mail/IP et les nouvelles photos Mongo sont réservées au propriétaire ; les anciens logs peuvent garder ces données, les anciennes photos Mongo sans propriétaire sont inaccessibles, les images disque restent publiques et la suppression SQL ne couvre pas explicitement Mongo, images et Joblib. Politique de durée, droits et suppression transversale restent à définir/implémenter. `SECURITE_UPLOADS.md`, `ANALYSE_MONGODB.md`. |
| **19. Avez-vous intégré des retours clients ?** | **Non, aucun retour explicite distinct des votes du compte test n'a été recueilli.** Les votes sont des labels utiles au pipeline, pas une étude de satisfaction. C'est une lacune du critère de la grille ; la prochaine validation doit recueillir un retour authentique et consentant. |
| **20. Où est le dataset sur le serveur Git ?** | Le code, les tests et un exemple synthétique sont suivis dans le dépôt local. L'export réel contient des préférences individuelles et reste privé hors Git ; un accès Git distant pour le jury n'est pas vérifié ici. Une publication exige un jeu minimisé/anonymisé licite, pas l'exposition des avis bruts. |
| **21. Quelle preuve de performance de l'application donnez-vous ?** | Des temps partiels datés : dataset médian 16,367 ms sur trois essais, prédiction Python 5,859 ms sur cinq essais, lectures SQL côté serveur. La génération complète, la latence mobile, le P95 et un SLA ne sont pas mesurés. `ANALYSE_BIG_DATA.md`. |
| **22. La démo avec 30 lignes synthétiques prouve-t-elle la qualité du RF ?** | Non. Elle prouve le trajet `/train` → `/predict`, l'isolation utilisateur et le fallback dans un dossier temporaire. Les performances de classification réelles locales proviennent des 64 avis et sont présentées séparément. `DEMO_ML.md`. |
| **23. Que faudrait-il pour démontrer un gain de recommandation ?** | Davantage d'avis diversifiés avec snapshot au vote, idéalement sur plusieurs comptes ; un protocole figé avant mesure ; et des lots de candidats avec jugements comparables pour calculer une métrique de classement. Il faudrait aussi un besoin métier et un retour utilisateur vérifiables. |
| **24. Quelle est votre principale décision d'ingénierie avant l'oral ?** | Ne pas remplacer le modèle ni retoucher les avis pour améliorer artificiellement un chiffre. Présenter l'architecture qui fonctionne, la baseline qui fait mieux, les limites de données/sécurité et les travaux nécessaires avant de déclarer un gain. |
