# FITS — Cycle de vie des données : état et décision proposée

**État du code au 13 octobre 2026.** Ce document distingue les contrôles effectifs des règles à décider. Il ne constitue ni une politique appliquée automatiquement ni une déclaration de conformité RGPD. Aucune suppression ou modification de données existantes n'a été exécutée pour le produire. La base Mongo est distante ; son statut d'environnement doit être confirmé avant toute opération réelle.

La [CNIL recommande de fixer les durées selon la finalité](https://www.cnil.fr/fr/passer-laction/les-durees-de-conservation-des-donnees). Pour la journalisation de sécurité, elle présente une [période glissante de six mois à un an](https://www.cnil.fr/fr/securite-tracer-les-operations), sous réserve du contexte. **Six mois est ici une proposition de départ, pas une obligation universelle ni une règle en vigueur dans FITS.** La décision doit préciser la finalité, les accès et les exceptions avant toute purge ou index TTL, notamment parce que les anciens logs peuvent contenir plus de données que les nouveaux.

## Pourquoi ne pas brancher immédiatement une suppression transversale

PostgreSQL, MongoDB et le disque n'ont pas de transaction commune. Supprimer d'abord SQL puis échouer sur Mongo laisserait des données sans compte ; supprimer d'abord les fichiers puis échouer sur SQL ferait perdre des images à un compte encore actif. Les anciennes photos Mongo et plusieurs images disque ne portent pas une attribution fiable dans leur stockage. Le code actuel renvoie pourtant « Compte supprimé avec succès » après la seule suppression SQL : **ce message ne prouve pas un effacement complet**. Le même écart existe pour la suppression admin.

Avant de changer ce parcours, préparer un environnement isolé avec comptes, tenues, avis, journaux, photos et Joblib **fictifs**. Établir l'inventaire de chaque ressource avec son propriétaire, puis tester : suppression normale ; ressource partagée ; ancienne photo sans propriétaire ; panne Mongo ; fichier absent ; échec disque ; échec SQL ; reprise après échec ; suppression admin. La réponse API et un journal technique limité aux statuts et compteurs doivent distinguer « terminé » de « incomplet », sans exposer les données ni les secrets. Seules les ressources attribuées avec certitude doivent être supprimées. Aucun script de purge ni TTL ne doit être pointé vers les bases actuelles pendant cette préparation.

**Priorité avant la soutenance :** montrer le correctif de lecture Mongo et la minimisation des nouveaux logs avec tests, puis présenter ce tableau comme une limite et un plan de validation concret. Une suppression inter-stockages précipitée créerait un risque de perte de données et une fausse promesse de conformité.
