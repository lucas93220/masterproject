# C5 — Programme IA, intégration et démonstration

## Parcours actuel

1. Le [mobile refondu](../../../mobile/src/screens/home.js) récupère la météo, demande une suggestion et affiche les pièces. Les états de chargement, erreur météo, avis et génération sont explicites ; un double appui ne crée pas deux avis.
2. [Node](../../../backend/controllers/tenueController.js) choisit jusqu'à cinq tenues compatibles avec le dressing. [Les règles](../../../backend/services/outfitCandidate.js) encadrent couches, chaleur, accessoires et couleurs ; elles ne sont pas des préférences apprises. Le réglage du 22/10 laisse une marge maximale de six degrés aux couches extérieures, plafonnée à 18 °C, sans les imposer, et n'affiche qu'un haut sous une veste ou un manteau. La nouvelle saisie de vêtement propose des plages thermiques par défaut, ajustables par l'utilisateur. [Les 85 features](../../../backend/services/outfitFeatures.js) restent alignées entre entraînement et prédiction.
3. Le [classement](../../../backend/services/rankCandidates.js) appelle désormais **pour chaque compte** le service articles/paires, qui vérifie identité, version et stockage. Node refuse aussi un score personnalisé sans version `items-pairs-v1`. Sans modèle compatible ou en cas de panne, le fallback explicite classe tout le lot avec la même règle ; il ne prend pas un ancien score RF à la place. Le RF reste disponible comme référence hors ligne et pour supprimer d'anciens artefacts.
4. Avant l'affichage, Node journalise la prédiction de la **tenue retenue** ; après like/dislike, le [contrôleur](../../../backend/controllers/evaluationController.js) fige le snapshot et déclenche le réentraînement personnel sur les seuls votes v2 admissibles. Le modèle courant ne remplace aucun Joblib RF. Le profil expose aussi la suppression de compte avec confirmation et reprise du nettoyage si nécessaire.

## Vérification et limites

Le [test d'intégration](../../../backend/tests/isolated/pipeline.test.js) utilise PostgreSQL et MongoDB temporaires et deux vrais FastAPI séparés : génération, vote, snapshot, dataset, isolation, prédiction, panne et fallback. [mlInteractions.integration.test.js](../../../backend/tests/mlInteractions.integration.test.js) relie Node au vrai service articles/paires avec les 85 features et identifiants ; [demo_interactions.py](../../../ml-service/demo_interactions.py) démontre sur **données fictives** deux préférences opposées et un fallback. Les parcours mobile et l'export Expo ont été vérifiés automatiquement ; la photothèque et les images privées restent à confirmer sur iPhone.

Sur le code actuel, le **22/10**, **191 tests backend (26 suites)**, **51 tests Python** et **64 tests mobile (neuf suites)** ont réussi. Le pont Node → vrai Python est inclus dans la suite backend ; ses autres tests utilisent des mocks et ne ciblent aucune base applicative. Les **huit scénarios avec stockages temporaires** ont réussi plus tôt le 22/10, avant le dernier réglage thermique, et n'ont pas été relancés depuis. Le lint mobile et les exports Expo web/iOS avaient réussi auparavant, sans changement mobile depuis. Les commandes figurent dans le [guide](../PREPARATION_SOUTENANCE.md#tests-et-demonstrations-sans-donnees-reelles). Ces tests prouvent l'exécution du programme, **pas** un avantage du modèle, la qualité du classement à cinq candidats ni une disponibilité en conditions réelles. Les deux services ML locaux doivent être disponibles et le téléphone doit joindre le backend sur le réseau de l'oral.
